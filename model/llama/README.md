# 架构选型与分布式策略说明
本项目 LLaMA 模型在架构上做了一个明确的决定：在 `model.py` 中不定义 `model_parallel_size` 参数，而是选择 Hugging Face `Accelerate` 作为分布式训练方案。

主要目的是：**将模型本身的计算代码与多卡运行的调度逻辑分开。**

---

## 一、 为什么不使用 `model_parallel_size`？

`model_parallel_size` 是张量并行（Tensor Parallelism）的常用参数。我们不使用它的原因如下：

1. **保持代码简单**：如果使用它，需要手动拆分线性层（Linear 层）并在前向传播中加入多卡通信代码。这会让基础的模型结构（如 GQA、RoPE）代码变得难以阅读和维护。
2. **提高兼容性**：如果代码中加入了多卡切分的逻辑，在进行单卡调试、CPU 测试，或者导出模型用于部署（如 ONNX/TensorRT）时，会遇到兼容性报错。
3. **满足当前需求**：对于 100B（千亿）参数以下的大模型，现有的显存分片技术（如 FSDP 或 ZeRO）已经足够满足多卡训练需求，不需要增加张量并行的复杂代码。

## 二、 为什么选择 `Accelerate`？

1. **不用修改模型代码**：开发者只需要编写普通的单卡 PyTorch 模型代码。`Accelerate` 会在后台处理多卡数据的分配和计算图的重组。
2. **通过配置切换环境**：将“使用几张显卡、用什么并行方式”写在外部配置文件（YAML）中。同一套模型代码，可以在单卡测试、多卡 DDP、DeepSpeed 或 FSDP 之间直接切换，不需要改动代码本身。

---

## 三、 主流分布式框架简明对比

为了说明上述决定，这里简单对比目前常用的几种大模型框架及其特点：

| 框架 / 工具 | 主要机制 | 优缺点 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **Megatron-LM** | **张量并行 (TP)**：将大型矩阵切分成多块，分发给多卡同时计算。 | **优点**：计算效率上限高。<br>**缺点**：需要大量修改模型代码，与多卡环境绑定较深。 | **100B+ 超大模型**的多机多卡预训练。 |
| **DeepSpeed / FSDP** | **显存分片**：将优化器状态、梯度和参数分摊到多卡，计算时拉取，用完释放。 | **优点**：无需修改模型代码就能解决显存不足问题。<br>**缺点**：多卡通信时间略多于张量并行。 | **7B-70B 级别大模型**的日常训练与微调。 |
| **HF Accelerate** | **统一调用接口**：对底层的通信和并行引擎进行上层封装。 | **优点**：使用简单，统一了不同框架的调用方式。 | **个人与中小型团队**的训练首选工具。 |
| **vLLM** | **PagedAttention**：将显存按页分配，用来管理 KV Cache。 | **优点**：减少显存碎片，提高并发量。<br>**缺点**：只能用于推理，不能用于训练。 | **线上环境**的模型推理与 API 服务部署。 |

## 四、 总结：本项目的技术分工

本项目的技术栈分工如下，各部分独立运作：

*   **模型定义**：标准 PyTorch 编写（`model.py` 保持普通单卡写法）。
*   **训练控制**：Hugging Face `Accelerate` 统一管理。
*   **显存优化**：通过配置文件调用 DeepSpeed (ZeRO) 或 FSDP。
*   **上线推理**：使用 `vLLM` 提供服务。
